# BBK 9288 应用移植踩坑与最佳实践

本文记录将 A 系列 GAM4980 模拟器移植到 BBK 9288 时遇到的主要问题。
重点不是复述最终代码，而是说明故障现象、根因、可靠做法和验证方式，供以后移植
其他 9288 应用时复用。

文中的结论分为三类：

- **已验证**：由 9288 SDK、官方 9288 程序反汇编、9288 模拟器或真机现象确认。
- **工程经验**：已在本项目中工作，但换固件或换程序后仍应复测。
- **风险提示**：目前证据不足，不能仅凭 API 名称或模拟器表现下结论。

## 一页总结

| 坑 | 常见现象 | 根因 | 最佳实践 |
|---|---|---|---|
| 混用 9588 SDK | 编译能过，运行卡死或调用错函数 | 两个平台的表布局和 ABI 不同 | 源码和构建只允许使用 `app_env_9288` |
| 工具链 ABI 不匹配 | API 参数错乱、随机死机 | 默认 S1C33 ABI 不符合 9288 GNU33 ABI | R6–R9 传参、R4 返回、保留 R15 |
| 把大数组放进 `.bss` | 启动长时间白屏 | 启动代码逐字节清零大块 `.bss` | 大型可覆盖缓冲区放 `.scratch` |
| 只使用 `NOLOAD` | 模拟器能跑，真机内存被覆盖 | KF2 只按文件载荷长度保留地址 | 在 `.scratch` 后放一个文件支持的 payload tail |
| 一次加载两片 ROM | 加载游戏时死机重启 | 两片 ROM 共 4 MiB，远超可靠连续堆空间 | ROM 文件常开，使用 4 KiB 分页缓存 |
| 认为“8 MiB SDRAM 等于可 malloc 8 MiB” | 大文件真机崩溃 | 堆碎片、系统占用和连续块限制 | 以约 1.5 MiB 连续分配上限做保守设计 |
| 猜 GUI 表偏移 | 白屏、卡死、调用到错误函数 | SDK 结构与 V1.5 固件私有表项存在偏移 | 先反汇编官方 9288 EXE，再核对函数签名和调用序列 |
| 直接写显存或错误刷屏 | 花屏、无刷新、永久重绘循环 | 9288 使用 GUI DC 和 LCD/HSDMA 提交流程 | 仿官方程序：`SysBltFrame` 后接 `InvalidateRect` |
| 在 `MSG_PAINT` 再次提交帧 | CPU 满载、界面卡住 | 每次提交又触发下一次 paint | `MSG_PAINT` 交给默认窗口过程完成传输 |
| 用 `GetTickCount()` 主动循环 | 模拟器正常、真机兼容性差 | 计时单位和消息调度精度不能想当然 | 用原生 `MSG_TIMER` 驱动游戏循环 |
| 把 Timer 参数当成精确帧率 | 节奏抖动或速度错误 | 固件 Timer 会量化、合并或延迟消息 | 用相位累加器调度核心，并在真机测量 |
| 调用未验证的游戏组合键 API | 真机或模拟器重启 | API 表项/前置状态不适用于普通应用 | 使用窗口 `MSG_KEYDOWN/MSG_KEYUP` |
| 把短按退出当关闭应用 | 游戏内无法使用 Exit | 物理退出键和应用生命周期混在一起 | 短按发送游戏 Exit，长按才关闭 9288 应用 |
| 游戏结束后重开选择器 | 从游戏菜单退出后白屏 | 线程级 Quit 和新窗口生命周期冲突 | 游戏正常结束应保存并返回 9288 桌面 |
| 只有一个 `.gam` 就自动启动 | 无法换游戏，也容易吃到启动按键 | 省略选择器破坏一致的输入流程 | 每次启动都显示文件选择器 |
| 直接修改唯一 NAND | 测试失败后环境不可恢复 | NAND 是有状态的，程序和存档会持续写入 | 每轮从原始 NAND 复制并生成独立测试镜像 |
| 发布包混入游戏或存档 | 版权和隐私问题 | 从测试目录直接打包 | 发布脚本使用白名单并检查 `.gam/.sav` |

## 1. SDK、ABI 与构建链

### 1.1 只能使用 9288 SDK

9588 版本可以作为算法和交互参考，但不能把它的头文件、API 表或打包脚本直接带到
9288 工程。最危险的情况不是编译失败，而是**编译成功后通过错误的函数指针运行**。

本项目的做法：

- `sdk/` 只接受 `app_env_9288`。
- `build_9288.py` 从指定 SDK 生成规范化头文件副本。
- `sdk/` 被 Git 忽略，仓库不发布 SDK，也不提供容易混淆的平台链接。
- 任何晚期 GUI API 都同时做结构偏移编译检查和固件运行时检查。

### 1.2 默认 S1C33 后端 ABI 不能直接用

9288 使用的 GNU33 ABI 与开源 S1C33 LLVM 后端默认约定不同：

- 前四个参数：R6、R7、R8、R9。
- 返回值：R4。
- R15 由 9288 加载器保留为应用数据指针，编译器不能自由分配。

本项目把差异保存在 `toolchain/9288-gnu33-abi.patch`，并用
`tests/9288_abi_probe.c` 保留最小 ABI 探针。移植新应用时应先验证一个只调用简单
SDK API 的小程序，再编译大型程序；不要用“大程序能启动”反推 ABI 正确。

### 1.3 KF2 是加载器格式，不是普通 ELF/EXE

构建过程先生成地址从 `0x02700000` 开始的 S1C33 ELF，再提取平坦载荷并封装为
9288 原生 KF2。以下字段必须作为打包测试的一部分：

- 机器类型为 9288。
- 模块号为 `8`，对应桌面的“娱乐”分类。
- 40×40 和 16×16 图标都是 2 bpp 四级灰度资源。
- `code_offset`、图标尺寸、总文件长度必须彼此一致。

不要只检查文件扩展名是 `.exe`；9288 桌面识别的是 KF2 头、模块和资源布局。

## 2. 内存：总容量不是可用连续堆

### 2.1 真机的可靠连续分配远小于 8 MiB

9288 有 8 MiB SDRAM，但这包括固件、GUI、文件系统、应用映像、堆和其他运行时状态。
根据其他开发者和本项目真机现象，单次 `malloc` 能可靠取得的最大连续块大约在
1.5 MiB 左右。这个数字不是公开 ABI 保证，只能作为保守工程边界。

因此：

- 不要同时 `malloc` 两片 2 MiB ROM。
- 不要按最大 2 MiB Flash 无条件分配。
- 不要把“模拟器分配成功”当作真机内存证明。
- 所有大分配都要失败可恢复，并在创建窗口后尽早完成。

### 2.2 ROM 使用流式分页缓存

`8.BIN` 和 `E.BIN` 各 2 MiB。正确做法是保持两个文件句柄打开，按需读取 4 KiB
bank，并用有限条目缓存热点页。本项目使用 32 条 bank cache，另外保留直接页和启动页。

这样把约 4 MiB 常驻 ROM 降为约 136 KiB 缓存，同时避免每次取指都访问 NAND。
打开 ROM 时还应验证精确文件长度；随机读取失败必须作为加载错误处理，不能向核心返回
未初始化数据。

### 2.3 Flash 按实际游戏大小分配

当前分配公式为：

```text
flash_size = align_up(0x15000 + game_size, 0x1000)
```

并限制不超过核心的 2 MiB Flash 上限。32 KiB RAM 使用静态缓冲区，不占用连续堆；
Flash 是运行时主要的大块堆分配。先读取 `.gam` 长度并验证头，再分配，避免错误文件把
尺寸计算推到异常范围。

## 3. `.bss`、`.scratch` 与 KF2 地址保留

### 3.1 为什么必须初始化 `.bss`

C 语言规定未显式初始化的静态对象在进入程序时为零。9288 的轻量加载器不会替应用
完成这一语义，因此启动代码必须清零真正的 `.bss`。错误不在于“清零 `.bss`”，而在于
把每帧都会完全覆盖的大缓冲区也放进 `.bss`。

早期版本需要清零约 76 KiB，逐字节循环造成明显白屏。当前做法是：

- 小型状态放 `.bss`，启动时以 32 字节展开循环清零。
- 屏幕帧、ROM cache、游戏 RAM、文件枚举缓冲等放 `.scratch (NOLOAD)`。
- `.scratch` 中的对象在首次读取前必须由业务代码完整写入。

### 3.2 单独的 `.noinit/NOLOAD` 仍可能被覆盖

KF2 没有 ELF program header，只携带一个平坦 payload 长度。若文件最后一个真实字节在
`.scratch` 之前，加载器只会按较短载荷保留地址；看似存在的 `NOLOAD` 尾部可能落入
其他内存用途。

本项目在 `.scratch` 后放置一个真实的 `0xff` 字节 `.payload_tail`。`objcopy` 因而会
把中间地址范围物化为文件内容，9288 加载器也会保留完整运行时映像。构建脚本随后检查：

- payload 长度必须等于 `__payload_end - 0x02700000`。
- 从 `__bss_start` 到 `__scratch_end` 的保留区必须实际存在于 payload。
- 保留区在文件中必须为填充值 `0xff`。

这条经验适用于所有带大块 `NOLOAD` 尾部的 KF2 应用。

## 4. GUI 表偏移与屏幕输出

### 4.1 不要靠 SDK 成员名猜固件函数

公共 9288 SDK 中 `SysBltFrame` 位于 GUI 表 `+0x59c`。V1.5 固件在晚期游戏 API 前
多了五个私有表项，官方程序实际使用的对应槽位是 `+0x5b0`。早期猜测 `+0x5c0`
会调用到别的函数，症状可以是白屏、卡死或重启。

可靠流程是：

1. 从同机型官方 EXE 找到 GUI relocation table 的调用点。
2. 核对参数寄存器、返回值、调用前后操作以及数据长度。
3. 用 SDK 结构做编译期断言，但把已验证的固件兼容偏移集中定义。
4. 不把 9588 的表偏移或函数签名迁移过来。

### 4.2 仿照官方《雷霆战机》的完整提交序列

9288 游戏界面提交的是完整 `0x4b00` 字节虚拟屏幕：

```text
320 × 240 × 2 bpp = 19200 bytes = 0x4b00
```

已验证的调用顺序是：

1. 为主窗口取得有效 Client DC。
2. 调用 `SysBltFrame(hdc, virtual_screen)`。
3. 调用 `InvalidateRect(window, NULL, FALSE)`。
4. `MSG_PAINT` 交给 `DefaultMainWinProc` 完成 GUI/LCD 传输。

不要在 `MSG_PAINT` 里再次调用 `SysBltFrame`；提交本身会引发 paint，再次提交会形成永久
重绘循环。已经消费的 `MSG_TIMER` 也不要继续传给默认窗口过程，否则可能产生额外刷新。

### 4.3 159×96 放大两倍的边界容易错一像素

游戏逻辑宽度是 159，但 packed stride 按 160 位存储，最后一位是 padding。正确结果是
318×192，放在 320×240 的 `(1, 24)`，左右和底部留白。

最佳实践：

- 用 4 项查找表一次展开两个源 bit，避免热点路径逐像素移位。
- 显式把 padding 对应的两个像素设为白色。
- 展开后整体右移一个像素，而不是把 160 位全部放大成 320 像素。
- 用截图脚本验证每个源像素严格对应 2×2 块和白色边距。

## 5. Timer、事件循环与性能

### 5.1 真机优先使用 GUI `MSG_TIMER`

主动调用 `GetTickCount()` 的 deadline 循环在模拟器上可以工作，但在真机存在兼容性和
调度问题。最终实现仿照官方游戏，使用窗口 Timer ID 1、speed 20，由 `MSG_TIMER`
通知外层事件循环推进模拟核心。

wndproc 收到 Timer 后只设置 `g_frame_tick_pending`，真正的解释执行放在消息派发返回后。
Timer 保持周期投递，重复消息由 pending 标志合并。这样回调不会重入，也不会在每批解释
完成后额外串行等待一个完整 Timer 周期。

### 5.2 不要把 Timer 参数直接等同于精确墙钟频率

9288 固件和模拟器的系统 tick 存在量化，事件泵落后时还可能延迟或合并 Timer 消息。
所以“speed 20”不能仅凭名称推导为完全均匀的 20 ms。实际计数显示它在当前 9288
固件和模拟器中约为 20 次消息/秒；旧代码误按 50 Hz 换算，只推进平均 1.2 帧/消息，
把整体速度限制在约 24 帧/秒。当前实现按 20 Hz 到 60 Hz 的比例，每次消息推进 3 帧，
模拟器中《伏魔记》由约 23.3 帧/秒提升到约 58.4 帧/秒。

风险提示：换固件、模拟器版本或负载后，应重新测量实际 Timer 投递频率和游戏速度；
不要把某次模拟器测得的帧率写成硬件保证。

### 5.3 解释器优化比微调 GUI 更值钱

本项目的主要计算成本是 6502 解释执行。默认使用 computed-goto 直接线程分派；
`--switch-dispatch` 只作为可移植回退。其他有效优化包括：

- 直接访问模拟栈，减少包装函数。
- ROM bank cache，减少 NAND 随机读。
- 2× 展开查找表和 32-bit 行复制。
- 只有核心报告画面变化时才提交帧。

优化时必须同时观察速度、输入响应和画面节奏。单纯提高“解释帧数”可能让 GUI 消息饿死。

## 6. 键盘、文件选择与退出语义

### 6.1 使用窗口按键消息，不调用未验证扫描 API

9288 有完整键盘，窗口 `MSG_KEYDOWN/MSG_KEYUP` 已足够。曾尝试调用
`GUI_ScanKeyForGameComboKeys`，结果是模拟器/真机卡死或重启；该 API 可能依赖官方
游戏框架的私有初始化，不能因名字合适就直接使用。

键位映射应集中在一个函数中。真机/模拟器可能分别把“退出”表现为 Escape 或 F12，
两种扫描码应进入同一套逻辑。

### 6.2 短按、长按和游戏结束是三种不同状态

正确语义：

- 短按 Esc/F12：向 GAM4980 核心发送游戏 `Exit` 键。
- 持续按住约一秒：关闭整个 9288 应用。
- 游戏从自己的系统菜单执行结束指令：写回存档，销毁窗口并返回 9288 桌面。

不要用不确定单位的 `GetTickCount()` 判断长按。当前实现累计已经验证可用的 GUI Timer
调度次数。更重要的是，不要把核心的 `shutdown_requested` 改成“重新打开文件选择器”：
9288 的 Quit 是线程/应用生命周期事件，销毁游戏窗口后又创建选择器会留下白屏。

### 6.3 文件选择器始终出现，并要求新的按下/释放

即使目录中只有一个 `.gam`，每次启动也显示选择器。这样用户可以明确确认文件，未来
添加游戏时行为也不改变。

启动应用的 Enter 可能仍处于按下状态。选择器必须：

- 打开后留足以覆盖桌面启动键释放的接受延迟。
- 只接受选择器内发生的新 `KEYDOWN`。
- 等到对应 `KEYUP` 后才销毁选择器和读取 NAND。

否则 Enter 会穿透到游戏、重复启动，甚至与窗口销毁和首次 NAND 读取竞争。

## 7. 文件系统、中文名与存档

9288 文件路径使用 `A:\`，固件按 GBK 处理中文文件名。模拟器制作 NAND 时还要注意
FAT short name；仅把 Unicode 文件复制到宿主目录并不保证固件能查到。

最佳实践：

- 固定运行目录为 `A:\gam4980\`。
- 枚举后只接受 `.gam`，并限制文件数量和名称缓冲区。
- `.sav` 与 `.gam` 同目录、同主文件名。
- 读写使用分块循环，检查短读、短写和 seek 结果。
- NAND 安装脚本在回包前修复 GBK short name，并再次读取验证文件尺寸。
- 保存只在 dirty 时写回；所有退出路径都要明确是否保存。

## 8. 图标、分类与设备风格

9288 应用图标不是一张无边框位图。桌面上的官方图标有统一圆角、投影和外框；直接把
9588 图标缩放或裁灰度会显得边缘缺失。

最终流程是：

1. 以原始 GAM4980 图标为内容参考生成/转换四级灰度图。
2. 复用 9288 SDK 官方图标框和阴影。
3. 生成 40×40 主图标和 16×16 小图标，两者保持同一内容识别。
4. 打包时逐字节核对 KF2 内图标与仓库资源一致。
5. 模块号设为 8，使程序出现在“娱乐”而不是“工具”。

## 9. 模拟器与真机验证策略

### 9.1 模拟器用于复现，不替代真机

`usb-connected=on` 本身不是 GAM4980 卡死的根因；同一模拟器中其他程序可正常运行。
排查时必须确认 NAND 中确实是刚构建的 EXE，不能只看宿主 `build/` 的时间戳。

每轮测试使用独立编号的 raw NAND：

1. 从只读基准 NAND 提取平坦 FAT 镜像。
2. 增量安装 EXE、ROM 和自备测试游戏。
3. 保留 `kernel.bin`，回包到新的 raw 文件。
4. 从 QEMU 命令行确认实际 NAND 路径和 `usb-connected` 状态。
5. 测试结束后只停止路径和 PID 都匹配的 QEMU/服务器进程。

不要覆盖唯一的原始 NAND，也不要把测试存档误当成发布输入。

### 9.2 最小回归矩阵

每次改动至少覆盖：

- 桌面核心 ASan/UBSan 冒烟测试，建议 10,000 帧。
- 9288 模拟器：娱乐分类 → 应用 → 文件选择器 → 游戏标题 → 剧情。
- 2× 几何检查：318×192、位置 `(1, 24)`、白色边距。
- 短按退出仍留在游戏或由游戏自行处理。
- 长按退出返回 9288 桌面。
- 从游戏系统菜单正常退出返回桌面，不白屏。
- 使用真机产生的 `.sav` 复测继续游戏和退出路径。
- 真机加载较大 `.gam`，观察是否因连续堆不足重启。

截图是重要的回归证据：程序“没有崩溃”不代表显示正确，白屏、旧帧残留和一像素偏移都
必须通过截图或真机观察发现。

## 10. 发布与仓库卫生

发布包应使用白名单构建，而不是压缩整个工作目录。本项目发布 ZIP 只允许：

```text
系统/程序/GAM4980.exe
gam4980/8.BIN
gam4980/E.BIN
```

发布前检查：

- KF2 magic、机器类型、模块号、图标布局、总长度。
- EXE 中图标与仓库资源完全一致。
- 两片 ROM 的大小和 SHA-256。
- ZIP CRC，并确认没有 `.gam`、`.sav`、SDK、NAND、诊断日志和临时截图。
- 记录 EXE/ZIP SHA-256，并让 GitHub Release 资产摘要与本地一致。
- 只暂存明确的源码和文档，不能使用会带入测试目录的无差别 `git add -A`。

ROM 是否能进入仓库与游戏版权是两个问题：本项目明确允许发布所需的 `8.BIN/E.BIN`，
但任何商业游戏 `.gam` 和玩家 `.sav` 都不进入仓库或 Release。

## 11. 推荐的开发顺序

移植新的 9288 程序时，推荐按以下顺序降低排错成本：

1. 用纯 9288 SDK 和正确 ABI 做最小窗口程序。
2. 验证 KF2 分类、图标和退出窗口生命周期。
3. 从官方同机型程序确认需要的私有/晚期 API。
4. 先显示静态 `0x4b00` 测试帧，再接动态画面。
5. 接入 GUI Timer 和键盘消息，不急着加入模拟核心。
6. 设计内存布局，先证明真机最大分配和 `.scratch` 地址保留。
7. 接入核心、ROM 流式缓存和存档。
8. 做文件选择器与完整退出路径。
9. 优化解释器和画面展开，逐项记录帧率变化。
10. 同时跑桌面 sanitizer、模拟器自动流程和真机测试。
11. 最后打包，并用白名单验证 Release 内容。

最核心的原则是：**9288 上“API 名称相同、模拟器能运行、总内存看起来足够”都不是
充分证据。每一层都要用正确 SDK、实际固件调用序列、明确的内存边界和可重复测试闭环。**
